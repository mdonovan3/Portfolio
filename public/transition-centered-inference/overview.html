An Epistemic Architecture for Longitudinal Scientific Inference

Martin Donovan  ·  July 2026  ·  Status: POC written, not yet run  ·  Early concept — feedback welcome
⚠ Working title — name TBD
The system is not primarily an AI model. It is a framework for managing conditional scientific belief over time.
Central research question: Can scientific theories become executable, versioned, queryable database objects? If yes, everything else follows naturally.

The Problem

In most longitudinal analysis — tracking language change over centuries, viral genome mutations over weeks, or patient biomarker trajectories over years — we have good tools for describing what changed and when. We have poor tools for systematically attributing why, in a form that is probabilistic, updateable, and computationally queryable.

A researcher working with longitudinal data today has causal reasoning — but it lives in three places that don't talk to each other: the analysis code that produced the result, the paper that interpreted it, and the researcher's own accumulated judgment about what patterns they've seen across their cohort. None of those are queryable, comparable across patients or specimens, or revisable when a follow-up observation changes the picture.

The current state: a tool produces output (a phylogenetic tree, a biomarker trajectory, a clonal evolution diagram). A domain expert reads that output and writes in a discussion section: "consistent with amyloid-driven tau propagation" or "likely represents immune evasion pressure." That causal attribution lives in a PDF. It cannot be updated when new evidence arrives, compared against thousands of similar attributions from a cohort, or queried across instances.

The practical question this framework asks: what if a researcher's ongoing causal interpretations — about their own data, in their own domain — were persistent first-class database objects that accumulate, revise, and become queryable over time? Not novel claims about measurement or analysis tools. Just a different data model for the interpretive layer that currently lives in PDFs and memory.

Defining Feature
What this framework offers a researcher that nothing in the current stack does: the ability to treat "I think this transition was driven by X with probability P, based on evidence E, under theory T, derived from dataset D" as a database row — one that can be queried across 500 patients, updated when a follow-up visit arrives, compared against a colleague's theory, and examined historically when a prior interpretation turns out to have been wrong.

Architecture Overview

Three First-Class Objects

Note: the core primitive the system stores is Inference — conditional inference under an explicit theory. Snapshots, transitions, and centroids are supporting objects. The current transition_inferences table name reflects the linguistics POC; the general form should eventually be inferences with transitions as one subtype — a population evaluated under a species concept, or a diagnosis evaluated under a clinical theory, has no transition but is still an inference.

Snapshot

The state of a system at a specific point in time. For dementia data: a patient visit — amyloid PET standardized uptake values, CSF phospho-tau, hippocampal volume, white matter hyperintensity burden, cognitive composite score. Stored as structured JSON with typed fields per data domain. This is the ground truth observational layer.

Transition

The change between two snapshots, modeled as a hypothesis about causation — not a diff. Each transition carries a cause_distribution: a probability vector over competing causal mechanisms, not a label. Example for a dementia progression event: 

{
  "cause_distribution": {
    "amyloid_accumulation": 0.50,
    "tau_spread":           0.30,
    "vascular_event":       0.10,
    "neuroinflammation":    0.10
  },
  "confidence": 0.72,
  "evidence_atoms": [
    { "type": "csf_ptau_increase",    "value": "+34%",   "weight": 0.41 },
    { "type": "wm_hyperintensity",    "value": "stable", "weight": 0.18 },
    { "type": "apoe4_status",         "value": "e4/e4",  "weight": 0.29 }
  ]
}

This distribution is updateable — a soft probabilistic state that shifts as new evidence arrives. Agent disagreement is preserved as variance: a measure of epistemic uncertainty, not noise to suppress.

Centroid

Multi-resolution aggregate of snapshots over a time window — individual visit → annual → decade → disease stage. Categorical features store full probability distributions, not just mode. Continuous features store mean + variance.

Critically, the spread statistics are a primary analytical signal, not just metadata. A century-level centroid for Latin in the 1st century CE might show low variance across all features — stable, well-documented, minimal change. The same centroid for the 4th century would show high variance and entropy across phonological and morphological features, reflecting rapid change under pressure from Germanic contact and administrative fragmentation. That contrast is visible at the centroid level before a single raw snapshot is examined — and it tells the meta-agent where to direct attention.

Each centroid therefore stores three layers:

  • Central tendency — mean (continuous), mode + probability vector (categorical)
  • Spread — standard deviation, IQR (continuous); entropy (categorical); overall instability score across all features
  • Attention signal — derived from spread: a flag or score indicating whether this window warrants detailed transition-level analysis. High entropy centroid → high attention priority. Adjacent centroids with diverging spread → likely change point boundary.

This makes the centroid layer a triage mechanism: the meta-agent scans spread statistics across all time windows first, ranks them by instability, and allocates specialist agent attention accordingly. Stable periods are summarized and passed over; high-variance periods are decomposed into their constituent transitions.

The Causal Grammar (the key architectural decision)

The architecture has a three-level hierarchy: 

Theory
  └── assumptions, ontology, predicates, calibration priors
       └── Grammar  (one executable component of the theory)
                └── Horn clause production rules (YAML → ProbLog)
                         └── Inference
                              └── cause_distribution, confidence, rule_trace

A theory is the full scientific framework — the set of assumptions, the ontology of causes, the predicate vocabulary, and the calibration priors. A grammar is one executable, versioned instantiation of that theory as probabilistic Horn clause rules. An inference is the result of evaluating a grammar against a specific evidence set. The grammar doesn't replace the LLM's learned representations — it constrains which inferences are structurally admissible under the current domain theory.

LLM agents propose candidate causal explanations from raw evidence; the framework then constrains and structures those proposals through a Probabilistic AND/OR Graph Grammar (POGG) encoding the domain theory. What's stored is not the output of a model run — it is a conditional inference under an explicit, versioned, queryable theory.

An additive weight model says: "tau increase contributes 0.4 to amyloid pathway score." That's blending. A grammar says: 

AMYLOID_DRIVEN_TRANSITION
  └─ AND(
       AMYLOID_ACCUMULATION_SIGNAL,
       APOE4_GENETIC_CONTEXT,
       NOT(DOMINANT_VASCULAR_BURDEN)
     )

VASCULAR_TRANSITION
  └─ AND(
       WMH_INCREASE,
       CARDIOVASCULAR_RISK_CONTEXT
     )

The AND/OR structure captures conjunctive causality — evidence combinations that additive weights flatten and misrepresent. The NOT is exclusionary logic that a weight matrix cannot express at all.

The grammar constrains admissible explanations under the current domain theory. Evidence that cannot be derived from active production rules becomes an explicit candidate for rule revision — not silently assigned an unsupported attribution. The grammar is not claimed to be complete; when evidence cannot be derived, that failure is itself a signal that the domain theory may need extension.

The Alzheimer's ATN (Amyloid-Tau-Neurodegeneration) biomarker framework is already a structured causal taxonomy of states. This would extend it to model state transitions with probabilistic causal attribution, rather than static classification.

Grammars are first-class versioned objects, not configuration files. Multiple grammars can coexist within a domain — a conservative grammar grounded in established theory and an extended grammar incorporating newer hypotheses can evaluate the same transition simultaneously, producing separate posteriors. The meta-agent coordinates across competing explanatory frameworks rather than selecting one truth. Grammar versioning means calibration can be tracked across versions: did v3 improve on v2 against known outcomes?

Persistent Domain Expert Agents and the Meta-Agent

A key design element distinguishing this from a standard multi-agent pipeline: specialist agents are not stateless function calls. They are persistent, serializable domain experts whose accumulated knowledge is stored in the database and carried forward across sessions.

Persistent Domain Expert Agents

Each specialist agent is assigned a specific domain scope — a language family, a patient cohort, a viral lineage, a tumor type. Over time, that agent accumulates:

  • A library of sound correspondences, mutation signatures, or biomarker patterns it has observed and validated
  • A set of open hypotheses it is actively tracking across new evidence
  • A record of past transition judgments — including cases where it was overruled by the meta-agent or revised when new evidence arrived
  • Calibration history: how well its confidence scores have tracked actual outcomes

The critical distinction: the agent's weights (the LLM) provide reasoning ability. The database provides domain knowledge. A new session doesn't start cold — it resumes where the agent left off, with full access to everything that agent has learned about its scope. This is the difference between asking a generalist model to analyze a new patient and asking a specialist who has followed a cohort for years.

In dementia terms: a "tau pathway agent" assigned to the ADNI cohort would, over time, build a structured record of every tau-related transition it has analyzed, the cause_distribution it assigned, whether the meta-agent agreed, and what subsequent biomarker data said. That accumulated record is its expertise — not stored in model weights, but queryable.

The Meta-Agent

The meta-agent does not analyze individual data points. It operates over the full graph of transitions, centroids, and agent outputs — across the entire cohort or corpus — and performs three functions:

  • Disagreement resolution. When two domain expert agents assign conflicting cause_distribution vectors to the same transition, the meta-agent does not average them. It reads the evidence atoms each agent cited, checks which have stronger grammar support, and either resolves the disagreement or flags it as genuinely uncertain (preserving both hypotheses rather than collapsing to one).
  • Cross-instance pattern detection. The meta-agent asks: which transition types cluster across patients, lineages, or languages? Do patients sharing the same causal derivation path (e.g., tau-dominated transitions with APOE4 context) show different treatment response curves than those whose transitions are vascular-dominated? This is not a query any individual domain agent can answer — it requires the full transition graph.
  • Task generation and feedback. When the meta-agent identifies a low-confidence region (a cluster of transitions where agent variance is high and evidence is sparse), it issues new analysis tasks back to the relevant domain expert agents — directing them to re-examine specific time windows, patients, or evidence types. The system is self-directing within its analytical scope.

The relationship between domain expert agents and the meta-agent is analogous to the relationship between specialist clinicians and a case conference — each specialist brings deep knowledge of their domain; the case conference synthesizes across them, resolves conflicts, and identifies patterns no single specialist would see.

Intellectual Lineage: Truth Maintenance Systems

The closest theoretical ancestor to this architecture is not expert systems or machine learning — it is Truth Maintenance Systems (TMS) and their assumption-based extension.

Doyle's TMS (1979) and de Kleer's Assumption-based TMS (ATMS, 1986) were built to maintain competing hypotheses with justification structures, revise beliefs as assumptions change, and preserve provenance across a reasoning session. ATMS explicitly supports multiple simultaneous assumption sets — different collections of beliefs that are each internally consistent — and tracks which conclusions are derivable under which assumptions. Later probabilistic ATMS extensions (1996) associated probability distributions with assumptions, allowing posteriors to be computed over derived conclusions. Uncertainty-aware truth maintenance is a mature research direction, not unexplored territory.

This means the following are not novel contributions of this architecture: maintaining competing hypotheses, recording justification structures, revising beliefs, or attaching probabilities to assumptions. Those are established.

What is novel is the operational context: ATMS was an in-memory, single-session reasoning engine. This architecture embeds probabilistic truth maintenance into a persistent longitudinal data platform — with temporal transitions as first-class database entities, asynchronous multi-agent evidence extraction, grammar versioning across competing scientific theories, and database-native querying of evolving causal beliefs across large datasets. The contribution is not a new truth maintenance system. It is truth maintenance concepts operating at data platform scale, over time.

A second key foundation is belief databases. Gatterbauer et al. ("Believe It or Not," VLDB 2009) formalized a relational database model where tuples are annotated with multi-agent epistemic belief statements — explicitly motivated by scientific databases where a community assembles, revises, and curates a shared repository. That work established the epistemic database as a first-class research object. This architecture extends the idea to causal beliefs (not just data tuple beliefs), adds probabilistic logic as the reconciliation layer, and adds temporal structure through transitions and centroids.

Taken together: belief databases established persistent queryable epistemic objects; ATMS established competing-theory management with justification provenance; probabilistic logic programming (ProbLog, MLNs) established grammar-constrained causal inference. This architecture integrates the three into a longitudinal, distributed research platform.

Formal Grounding: The Prolog / Probabilistic Logic Connection

The causal grammar production rules are, formally, Horn clauses — the same structure that underlies Prolog. The mapping is exact:

POGG concept Prolog analog
Production ruleHorn clause (head :- body)
AND-edgeConjunction in rule body
OR-edgeMultiple rules with same head
NOT-edgeNegation as failure (\+)
Evidence atom (terminal)Ground fact
Causal derivationProof tree
Posterior over derivationsProbLog query probability
LLM agent as evidence sourceProbabilistic fact / neural predicate

Written as actual Prolog, a production rule looks like: 

substrate_transition :- phonology_pressure, lexical_mismatch.
phonology_pressure   :- inventory_shift.
phonology_pressure   :- markedness_anomaly.           % OR via multiple rules
amyloid_transition   :- amyloid_signal, apoe4_context, \+ dominant_vascular.

Standard Prolog is deterministic — a query succeeds or fails, no probability. ProbLog closes this gap: facts carry probabilities, and queries return P(goal is provable | probabilistic facts) — essentially P(cause | evidence), which is the core POGG computation. DeepProbLog (Manhaeve et al., 2018) adds neural networks as the ground-fact evidence layer — structurally almost identical to this architecture, with LLM agents in place of gradient-trained networks.

Nested Inference — A Precise Description

Prolog has a long tradition of meta-interpretation — Prolog programs that interpret other Prolog programs. ProbLog is exactly this: a probabilistic meta-interpreter that runs the causal grammar (object-level Prolog) and tracks probability mass across the proof search instead of returning true/false. The meta-agent adds a third level, reasoning over the outputs of many probabilistic inference runs across instances. The full stack: 

LLM agents             →  produce probabilities for ground evidence facts
Ground facts           →  evidence_atoms with probability weights
Causal grammar         →  Horn clauses (the domain theory)
Probabilistic          →  ProbLog / inside algorithm: Prolog reasoning ABOUT
meta-interpreter          Prolog proofs, tracking probability across derivations
Meta-agent             →  synthesis over many inference runs, cross-instance

Layers 3 and 4 form a nested inference structure: a probabilistic meta-interpreter reasons about the proofs produced by the causal grammar, tracking probability across derivations. The meta-agent adds a third level — synthesis over many inference runs. This is not just an analogy — it maps to a mature field (Probabilistic Logic Programming) with working implementations.

Practical implication: The production rules can be written as actual Prolog clauses and tested with ProbLog today, before any custom inference machinery is built. ProbLog is one possible inference backend — it uses probabilistic semantics over Horn clause derivations. Tomorrow the inference layer could be swapped for Markov Logic Networks, Probabilistic Soft Logic, or weighted Answer Set Programming without changing anything above it. Markov Logic Networks in particular offer a learning framework for deriving rule weights from labeled data, directly applicable to the calibration problem.

A note on provenance. The pipeline from evidence atoms through rule firing to posterior to revision history is structurally a provenance graph with epistemic semantics — closely related to the W3C PROV model and the why-provenance literature (Green et al., PODS 2007). This connection is worth exploring before building a custom justification chain representation: provenance models for scientific workflows are a mature area and may provide data structures and query patterns directly applicable here.

Rule Authoring and Storage

Production rules are first-class data objects stored in the database, not code in a file. A rules table holds one row per rule, domain-scoped, with the human-authored definition, its compiled Prolog form, an optional probability weight, and a literature citation. The grammar the inference engine runs is compiled at query time by loading the active rules for the requested domain.

This has three practical consequences: rules are runtime-editable (no container restart), auditable (full history of what rules fired for which transitions), and domain-scoped (the linguistics grammar and the virology grammar coexist in the same table, loaded selectively). Adding a production rule does not require touching the inference engine, agent framework, or API.

The authoring format is YAML — not a custom DSL and not raw Prolog. YAML is widely adopted across technical disciplines; a clinician, biologist, or linguist has almost certainly encountered it through config files, pipeline tooling, or infrastructure-as-code. No new syntax to learn. Editors, schema validators, and linters already exist. A domain expert can author rules from a template without knowing Prolog: 

# Linguistics — substrate influence rule
- rule: substrate
  domain: linguistics
  head: substrate
  conditions:
    all_of:
      - phonology_overhang
      - lexical_continuity
    none_of:
      - contact
  literature: "Thomason & Kaufman (1988) Language Contact, Creolization, and Genetic Linguistics"
  weight: 0.75

# Neurodegeneration — amyloid pathway rule
- rule: amyloid_driven_transition
  domain: neurodegeneration
  head: amyloid_pathway
  conditions:
    all_of:
      - amyloid_accumulation_signal
      - apoe4_context
    none_of:
      - dominant_vascular_burden
  literature: "Jack et al. (2018) NIA-AA Alzheimer's disease framework"
  weight: 0.80

The YAML compiles to Prolog mechanically — all_of items become a conjunction, none_of items become negation-as-failure (\+), multiple rules with the same head produce OR alternatives. A domain expert reads a rule file and sees the causal theory of the domain in plain structured text, with citations attached. The rules function as living documentation alongside being machine-executable.

The Predicate Registry (the key engineering boundary)

A predicate registry table records which evidence atom names exist for each domain and which feature extractor produces them. This is the typed API boundary between the measurement layer and the reasoning layer: 

Feature extraction  →  Predicate Registry  →  Rule Engine
  (LLM agents)          (typed contract)       (probabilistic logic)

Without this boundary, an LLM agent can output anything and the rule engine receives arbitrary text. With it, agents produce only named, registered predicates — and a rule that references an unregistered predicate is a validation error before it reaches the inference engine. This is a significant reduction in entropy: it makes domains modular, feature extractors substitutable, and rule authoring verifiable. It is also what allows a domain expert to write production rules without knowing how the underlying measurements are produced — the registry is the interface specification between those two concerns.

What Already Exists

Theoretical Foundations This Architecture Builds On

Belief databases (Gatterbauer et al., VLDB 2009) — formalized a relational database model with multi-agent epistemic belief annotations, motivated by scientific community curation. Establishes that persistent queryable epistemic objects are a viable database-layer concept.

Truth maintenance and ATMS (Doyle 1979, de Kleer 1986) — competing hypothesis management with justification provenance. Probabilistic ATMS extensions (Liu & Bundy 1996) attach probability distributions to assumption sets. Establishes the competing-theory and revision foundation.

Probabilistic logic programming (ProbLog, Markov Logic Networks, DeepProbLog) — grammar-constrained causal inference with probabilistic Horn clauses. Establishes the reconciliation layer foundation.

Closest Deployed Systems

SemMedDB (Kilicoglu et al., Bioinformatics 2012) — ~96 million subject-predicate-object triples from PubMed, with causal predicate types (CAUSES, INHIBITS, TREATS), normalized to UMLS concepts, every triple linked to its source PMID. A large-scale persistent queryable scientific causal knowledge base. Gap: no probabilistic weights on beliefs; no competing-theory structure; no Horn clause reconciliation; no temporal transitions; revision not first-class.

ChronoMedKG (2025) — adds temporal structure to SemMedDB-style triples, with credibility scores and disease-stage temporal components. Closest existing system to the longitudinal dimension. Gap: same as SemMedDB for competing theories, probabilistic logic, and first-class revision.

Domain Analysis Tools

Model-Based Hypothesis Testing (MBHT) in virology (Frontiers, 2025) — Bayesian posteriors over competing causal hypotheses for viral evolution. Validates the cause_distribution concept. But MBHT is flat (no AND/OR grammar), post-hoc, and not integrated into a queryable transition database.

COSMIC mutational signatures in cancer genomics — flat W-matrix decomposition of mutational causes. No compositional structure, no temporal transitions as first-class objects.

BEAST X (Nature Methods, 2025) — gold standard for viral phylogenetic inference. Causal attribution remains post-hoc human interpretation.

⚠ Honest Gaps — What I Don't Know
  • Production rules don't exist yet. For any domain, the causal grammar must be grounded by a domain expert. Without that grounding the rules could be systematically wrong in ways that look correct — the architecture cannot compensate for a bad theory.
  • No calibration strategy defined. Overconfident causal attribution is a known failure mode in probabilistic systems. How rule weights are learned from or validated against known outcomes is an open problem.
  • POC written, not yet run. A linguistic proof of concept (Germanic branch validation with ASJP wordlist data) is implemented in Docker Compose but not yet executed. No empirical feedback yet.
  • Adaptive temporal window segmentation unspecified. How to draw period boundaries from transition density rather than fixed calendar intervals is an open design question.
  • Scale overhead unknown. The multi-agent ensemble adds infrastructure cost. Whether that cost is justified at the dataset sizes typical of a research team has not been evaluated.
  • The architecture makes reasoning reproducible — it does not fix bad measurements. If feature extraction produces poor evidence atoms, the downstream probabilistic logic will be precise and wrong. The predicate registry enforces structural validity, not empirical accuracy.

Theory Perturbation and Structural Sensitivity Analysis

Because grammars are first-class versioned objects and every inference is tagged to the grammar that produced it, the system supports a form of analysis that is categorically different from standard sensitivity analysis.

Standard sensitivity analysis asks: "What happens if parameter λ changes?" This system asks: "What happens if Rule 17 doesn't exist?" Those are different questions. The first operates on numerical weights within a fixed model structure. The second — theory perturbation — operates on the causal structure itself.

A researcher encodes a set of theoretical assumptions as a grammar and runs it against transitions where the outcome is known. The resulting cause_distribution either converges on the known record or it doesn't. They then remove a rule, add a constraint, or swap a causal pathway — and rerun under the new grammar version. The transition_inferences table holds both results for the same transitions: the comparison is a query, not a second analysis from scratch.

The practical form: a researcher suspects that substrate influence, not drift, was the primary driver of a set of transitions. They encode that hypothesis as a grammar, run it against transitions with known historical outcomes, and measure whether it outperforms the drift-primary grammar. If it does, there is now a quantified, reproducible, queryable argument for revising the theoretical consensus. If it doesn't, the null hypothesis survives — and the full reasoning chain is stored, not discarded.

This capability is inherited from the ATMS lineage: ATMS environments were designed to answer exactly this question in diagnostic reasoning — "what if I assume this component is faulty instead? Does that explanation fit the observation set better?" The architecture extends that to longitudinal scientific inference with probabilistic grammars and a durable queryable store.

Pattern Discovery and the Theory Refinement Loop

The system surfaces patterns the current grammar cannot explain. The meta-agent scans for high instability_score centroids and transitions where competing grammars disagree sharply — both are signals that something in the data is not accounted for by the current causal theory. These aren't errors; they're discovery opportunities.

This creates a feedback loop between pattern recognition and grammar refinement:

  1. Discover — the meta-agent flags unexplained transitions and high-disagreement regions; the researcher examines what the current grammar is failing to account for
  2. Hypothesize — the researcher proposes a new causal mechanism or structural rule that might explain the anomaly
  3. Encode — author the hypothesis as a new grammar rule in YAML; the system creates a new grammar version linked to the prior via parent_grammar_id
  4. Test — rerun the affected transitions under the new grammar; transition_inferences holds the new posteriors alongside the old ones without overwriting them
  5. Evaluate — does the refined grammar converge better on known outcomes? Does disagreement decrease?
  6. Promote — if yes, mark the grammar version active; the improvement is measurable and the full provenance chain is preserved
  7. Repeat — the refined grammar produces new inferences, which may surface new anomalies, restarting the loop

Each iteration is fully traceable: what changed, which transitions it affected, and whether convergence improved. The loop is the scientific method — observe anomaly, hypothesize, encode, test, revise — formalized as a set of queryable database operations rather than a narrative in a lab notebook.

Automated grammar induction (an LLM proposes candidate rules grounded in literature; a domain expert validates) would tighten the loop further — this is noted as a future capability. The manual loop is fully supported by the current design.

Open Questions
  1. Grammar maintainability at scale. Can a probabilistic logic grammar remain maintainable once a domain exceeds ~500 predicates? Is there a known threshold where rule systems of this type become intractable to author and debug?
  2. Horn clause expressiveness limits. What classes of causal hypothesis cannot be represented as Horn clauses? Are there patterns in longitudinal structured data — temporal ordering constraints, feedback loops, graded causation — that require richer representations?
  3. Competing grammars. When two domain experts encode different but internally consistent causal theories, the system produces separate posteriors per grammar rather than arbitrating. Is grammar versioning and provenance sufficient to make that comparison useful, or does it require a more principled reconciliation mechanism?
  4. Rule weight learning. Should production rule probabilities be learned globally from labeled data, or personalized per specialist agent based on that agent's calibration history? The latter is more expressive but significantly more complex.
  5. Grammar induction. Can rule authoring be partially automated — an LLM proposes a candidate Horn clause grounded in literature, a domain expert validates, and the grammar evolves incrementally? What are the known failure modes of human-in-the-loop probabilistic rule acquisition?
  6. Is this useful at research team scale? The system is designed to be deployed per research team and domain, not as a global infrastructure. Does that deployment model match how research teams actually want to manage interpretive knowledge about their longitudinal data?

General Applicability: A Domain-Agnostic Framework

The inference engine — the Redis/Postgres coordination layer, agent protocol, POGG parser, and centroid computation — is domain-agnostic. The grammar is not: ontology, causal rules, evidence mapping, and calibration are each a new project for each new domain. Generalizability means a team can deploy the same stack with a different grammar and feature extractor; it does not mean a new domain is cheap or automatic. Below are the domains where this framing has been analyzed in detail, with notes on how the mapping works and where the closest existing tools fall short.

What Generalizability Means in Practice

"Domain-agnostic" is a claim that needs a concrete definition. The intended scale is a research team deploying one instance for their domain. Each deployment is scoped to a domain and a team; the generalizability is in the codebase, not in runtime coupling between deployments.

Standing up a new instance for a new team or domain requires three things and no code changes to the stack:

  1. Domain registration — insert a row naming the domain and its cause axes
  2. YAML production rules — author the causal grammar for the domain; the system compiles these to Prolog and loads them at inference time
  3. Feature extractor — implement the domain-specific functions that map raw measurements to the named evidence atom predicates

The inference engine, coordination layer, API, and centroid computation are unchanged across deployments. The shared infrastructure cost is paid once per instance; each new team or domain pays only for their feature extractor and rule set.

Cross-Domain Analysis: A Secondary Concern

Whether the causal grammar structure for "substrate influence" in linguistics is formally analogous to "host immune landscape pressure" in virology is a genuinely interesting empirical question — one this architecture makes askable. But cross-domain comparison is not the primary operational mode. It would be an export and federation concern: standardized transition output formats, separate meta-analysis step, linked results between deployments. A research team using this system for their own domain data does not need to know about or connect to other deployments. That connection, if valuable, is built later on top of the persistent store — not designed in as a runtime requirement.

A natural eventual addition would be import/export and sharing utilities: standardized formats for publishing a deployment's transition graph, grammar definitions, and calibration history alongside research data — so that teams can compare interpretive knowledge with collaborators running the same stack on different cohorts, without requiring live integration between deployments.

Possible Future Features

  • Portable computation units. A self-contained capsule bundling the exact data subset required (snapshot pairs, grammar version, feature predicates) with the inference logic — packaged so it can be dispatched to any execution environment and return results to the persistent store. The core concept is the closure: data and logic travel together, execution is location-independent, results flow back. The capsule format is the stable abstraction; the dispatch interface is pluggable. A Postgres-backed task queue (each capsule is a claimable row containing a query that resolves the exact data needed plus grammar references), a Redis queue, a shared filesystem, or a cloud batch job queue all become viable targets without changing the capsule format — the destination could be a cluster at a research facility, a cloud job, or a collaborator's instance. A scheduler component could watch the queue depth and autonomously dispatch when workload crosses a threshold — no manual invocation required. Pluggable backends: SLURM (via SSH or the SLURM REST API, submitting array jobs on a research facility cluster), AWS Batch (containerized workers on-demand), or Google Cloud Batch — each adapter speaks the capsule format; the rest of the system is unchanged. The system detects the batch, dispatches it, monitors for completion, and harvests results back into Postgres. This also serves as a reproducibility artifact: the capsule that produced a given inference is a complete, independently executable record of what data and rules were used.
  • Import / export / sharing utilities. Standardized formats for exporting a deployment's transition graph, grammar definitions, and calibration history — so research teams can publish their interpretive knowledge alongside data, share with collaborators, or load results from another team's deployment for comparison. Not a live integration requirement; a data exchange format.
  • Grammar induction assistance. An LLM proposes candidate Horn clause rules grounded in literature; a domain expert validates, edits, or rejects them; accepted rules enter the registry. Human-in-the-loop rule authoring rather than purely manual. Related to the inductive logic programming literature (ILASP, ProbFOIL).
  • Rule weight learning. Currently rule weights are manually assigned or left as placeholders. Markov Logic Networks provide a learning framework for deriving weights from labeled data — applicable once a deployment has accumulated enough canonical transitions with known outcomes to calibrate against.
  • Adaptive temporal window segmentation. Rather than fixed decade or century buckets, draw centroid window boundaries from transition density — periods of rapid change get finer resolution, stable periods get coarser. Requires a changepoint detection step before centroid computation.
  • Rule-level diff tracking. The grammar versioning design already tags every inference with the grammar version that produced it, and grammar lineage is tracked via parent_grammar_id. What's not explicit is a record of exactly which rules changed between versions — the equivalent of a git diff at the rule level. A grammar_rule_changes table (or a superseded_by foreign key on individual rules) would make it possible to ask "which rule change between v1 and v2 shifted the posterior on this transition" without manually diffing rule sets.
