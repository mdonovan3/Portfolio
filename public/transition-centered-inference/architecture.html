The Stack at a Glance

ComponentTechnologyConceptual Role
Epistemic Store PostgreSQL Persistent, queryable home for all first-class objects: snapshots, transitions, grammars, inferences, centroids. The canonical record that survives restarts, revisions, and time.
Coordination Layer Redis Ephemeral task queue, atomic job claiming, candidate pool, agent heartbeats. Hot coordination state that doesn't need to survive a restart.
Grammar Engine ProbLog (HTTP service) Evaluates the causal grammar against evidence atoms. Produces a probability distribution over competing causal explanations for each transition.
Agent Workers Python (×N parallel) Distributed evidence extractors. Each agent claims a transition task, extracts evidence atoms from snapshot feature vectors, calls the grammar engine, and returns a candidate result.
Meta-Agent Python (single, cyclic) Synthesis and discovery. Harvests candidates from Redis, promotes stable results to Postgres, computes centroids, flags instability signals, and surfaces anomalies for researcher attention.
REST API FastAPI Researcher interface and external integration point. Accepts new data, exposes query endpoints, triggers batch dispatch, serves results.

Stack Architecture

How the components connect. The canonical store sits at the center; everything reads from and writes to it. Redis is the coordination membrane between agents and the meta-agent. The ProbLog service is isolated so the grammar can be reloaded without restarting workers.

The Four First-Class Objects

Every piece of knowledge the system accumulates is one of four types of object in Postgres. All other tables serve to link, version, or annotate these four.

The Process Cycle

One full cycle from raw data ingestion to researcher discovery. The cycle repeats continuously; the grammar refinement path (steps 8–10) is triggered by the researcher in response to discovery signals from the meta-agent.

Component Notes: Why Each Technology

PostgreSQL — The Epistemic Store

postgres

The canonical, durable record of everything the system knows. All four first-class objects — snapshots, transitions, grammars, centroids — live here. Every inference result is a row in transition_inferences; every grammar version is a row in grammars with a parent_grammar_id linking to its ancestor.

Why not a graph database? The knowledge here is structured and relational, not schema-free. The connections between objects (snapshot → transition → inference → grammar) are fixed and queryable with SQL. A graph DB would add traversal flexibility the use case doesn't need and would lose the JSONB feature vectors, window functions, and transactional guarantees that make the centroid and calibration queries tractable.

Why not a vector store? Vector stores retrieve by similarity. This system retrieves by provenance, grammar version, and confidence threshold — structured queries, not nearest-neighbor search. Similarity is computed at the application layer if needed.

Conceptual role: persistence makes inference revisable. Without a durable store, a causal claim exists only in the context that produced it. With Postgres, it exists as a queryable object across time, sessions, grammar versions, and dataset versions.

Redis — The Coordination Layer

redis

Ephemeral state only: the work queue (ZSET work_queue:global), candidate pool, agent heartbeats, and atomic task claims (SET NX EX — claim a task or fail immediately without blocking). Nothing in Redis needs to survive a restart; if Redis goes down, the canonical store in Postgres is intact and the queue can be rebuilt.

Why not just Postgres for queuing? Redis's atomic operations and in-memory speed make it the right tool for high-frequency coordination state: many agents polling for tasks, heartbeats expiring, candidates being harvested. A Postgres queue would work but adds row locking contention at scale. The separation also keeps the epistemic store clean — coordination noise doesn't pollute the canonical record.

Conceptual role: Redis is the space where work happens before it becomes knowledge. Candidates live in Redis until variance is low enough and confidence is high enough to promote them to Postgres. The promotion threshold is the epistemic gate.

ProbLog Service — The Grammar Engine

problog fastapi

A dedicated HTTP service that accepts an evidence atom set and a grammar reference, evaluates the Horn clause production rules, and returns a probability distribution over causal explanations (cause_distribution) plus the rule trace (rule_trace) showing which clauses fired and with what weight.

Why a separate service? Isolation. Grammars can be reloaded via POST /reload without restarting agents. The grammar engine can be scaled independently. Alternative inference backends (MLNs, weighted ASP) could be swapped in behind the same HTTP interface without changing agent code. The service boundary enforces the predicate registry contract: evidence atoms are the typed interface between feature extraction and inference.

Conceptual role: the grammar engine is what makes LLM agents produce structured causal claims rather than fluent narratives. The POGG constrains which derivations are structurally admissible — a proposed cause that violates the grammar's production rules is a parse failure, not a low-probability output. This is the mechanism that keeps agents as evidence producers rather than unconstrained reasoners.

Agent Workers — Distributed Evidence Extraction

python ×N parallel

Each agent is a polling worker: claim a task from Redis, load the relevant snapshots from Postgres, extract evidence atoms from the feature vectors (domain-specific functions), call the ProbLog service, write a candidate result to the Redis pool. Workers are stateless within a task — they carry no accumulated state between runs.

Why N parallel agents rather than one inference pass? Context scaling is a hard constraint: a full corpus of transitions can genuinely exceed a single model call's context window. Parallel sharding is the only way to process corpora larger than context. This is map-reduce: agents are the map step, the meta-agent is the reduce step. The architecture is not agent-aesthetics — it is the only viable design for large corpora.

Conceptual role: distributed evidence extraction separates the question of "what does the raw data say?" (agent's job) from "what causal explanation is best supported?" (grammar's job) from "what is the consensus across many runs?" (meta-agent's job). Each layer does one thing.

Meta-Agent — Synthesis, Triage, and Discovery

python single cyclic process

The meta-agent runs a continuous cycle: harvest candidate results from Redis, check variance and confidence thresholds, promote qualifying candidates to transition_inferences in Postgres, compute centroid aggregates, and scan for instability signals. It does not evaluate evidence atoms — that is the agent's job. It synthesizes across many agent outputs.

Why not merge the meta-agent into the agents? The meta-agent's role is cross-run synthesis and anomaly detection. It needs to see the whole candidate pool, not just one task at a time. It operates on aggregate patterns (instability across a temporal window, disagreement between competing grammars) that no single agent can see. Separation of concerns keeps the system auditable.

Conceptual role: the meta-agent is where pattern discovery happens. High instability_score centroids and high-disagreement transitions are the signals that the current grammar is failing to account for something in the data — the starting point for the theory refinement loop.

REST API — Researcher Interface

fastapi port 8000

The API is the boundary between the running system and the researcher. Inbound: new snapshots, grammar reloads, batch job triggers. Outbound: transitions and their cause distributions, centroid instability rankings, grammar version history, calibration queries.

Possible future extension — large-scale compute offload: For analyses that exceed what a single deployment can process in reasonable time, the API is the natural point for dispatching work atomically to an external compute engine. The concept: package the exact data subset and grammar version needed for a computation into a self-contained unit (a portable task capsule), hand it off to a larger resource, and receive results back into the epistemic store. Candidate targets include SLURM clusters (common at research universities and facilities — job submission via SSH or the SLURM REST API), AWS Batch, and Google Cloud Batch. The capsule format would be the stable abstraction; the dispatch backend would be pluggable. This is a design idea, not a current capability.

Conceptual role: the API surfaces the epistemic store in queryable form. A researcher asking "which transitions changed their cause distribution most significantly between grammar v1 and v2?" is answered by a query through the API — not by re-running the analysis.
